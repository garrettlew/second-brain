**1\. Motivation**

Multi-agent LLM systems (MAS) have become the dominant architecture for complex AI applications \[1, 2, 3\]. Frameworks like AutoGen, MetaGPT, and AgentVerse make it straightforward to decompose a monolithic prompt into a pipeline of role-specialized agents. However, this decomposition incurs significant, often unmeasured costs. Cemri et al. \[4\] catalogs 14 failure modes across 1,600+ multi-agent traces in the first MAS comprehensive dataset (MAST-Data) and unified taxonomy (MAST). The paper demonstrates that performance gains often remain minimal compared to single-agent frameworks or simple baselines like best-of-N sampling. We compare a single general-purpose agent against a three agent pipeline using a note-taking system (tagging, summarization, cross-note linking) in Obsidian as a tractable testbed. We also add a fourth agent, an overseer, to see if there are any improvements to MAS.

**2\. Research Question(s)**  
*Does a pipeline of specialized agents produce higher-quality note enrichment than a single general-purpose agent?*  
*Does adding an overseer agent address failures from MAS?*

**3\. System Design**

Both pipelines interact on the same notes but differ in their execution strategies.

### I. Baseline Architecture: Monolithic Single Agent

A single, general-purpose LLM agent.

**Mechanism:** This pipeline utilizes a single API call encompassing a comprehensive prompt (e.g., "Analyze this note: append relevant tags, write a summary, and suggest related topics").

**Purpose:** To benchmark the efficiency, coherence, and accuracy of a generalized approach against specialized task decomposition.

### II. Proposed Architecture: The Multi-Agent Pipeline

The experimental pipeline replaces the monolithic call with a sequential pipeline of lightweight, highly specialized AI agents. Each agent operates with a narrow system prompt, executing a single distinct function and passing structured data downstream. The multi-agent pipeline consists of the following components:

### Orchestrator:

Acts as the control plane for the pipeline. It triggers each agent in the correct sequence, handles API routing, and manages the state by passing the structured output from one agent to the input of the next.

### Stage 1: Tagger Agent (Classification & Metadata)

**Input:** The markdown file of the Obsidian note.

**Function:** Analyzes the text to classify the note and extract a structured list of relevant topical and categorical tags.

**Output:** A structured array/list of tags, which is passed back to the Orchestrator.

### Stage 2: Summarizer Agent (Synthesis)

**Input:**  The markdown file plus the tags generated by the Tagger Agent.

**Function:** Synthesizes the core concepts of the note into a concise 2–3 sentence summary. By using the tags from the previous stage as grounding context, the Summarizer can weigh the most relevant themes more accurately.

**Output:** A concise text summary.

### Stage 3: Linker Agent (Retrieval-Augmented Generation)

**Input:** The generated summary and tags.

**Function:** Instead of relying on a broad keyword search of the original note, the Linker Agent uses the highly distilled summary to query a ChromaDB vector store containing the user's existing knowledge base.

**Output:** The agent retrieves the top contextual matches and outputs the 3 most relevant past notes, appending a distinct, one-line justification explaining why each note is connected to the current one and filtering out non related notes.

### Stage 4: Overseer Agent (The Manager)

The Overseer’s role is to ensure the integrity of the system:

**Task Routing & Logic:** Instead of a rigid sequence, the Overseer determines if a note actually needs all steps. For example, if a note is too short to be summarized, the Summarizer stage can be skipped.

**Quality Control:** The Overseer inspects the output of each worker. If the Tagger Agent produces irrelevant or "hallucinated" tags that don't exist in the user's defined schema, the Overseer can trigger a "retry" with a corrective prompt.

**Contextual Synthesis:** Before the final write-back to Obsidian, the Overseer performs a final "sanity check" to ensure the summary, tags, and links are cohesive and logically consistent with one another.

**4\. Evaluation Plan**

To assess the performance difference between the baseline single-agent and the managed multi-agent pipeline, both systems will process a fixed dataset of about 15–20 notes from the Obsidian vault. The outputs from both architectures will be evaluated side-by-side using the following four metrics:

**Tag Relevance (Score: 0 or 1\)** is a binary metric evaluating the generated tags.  
0: Irrelevant, overly broad, or hallucinated tags.  
1: Relevant, highly descriptive tags that fit the vault's context.

**Summary Faithfulness (Score: 1–3)** is a qualitative measure of how accurately the summary distills the source note without introducing external information.  
1: Misses the key point or hallucinates facts.  
2: Adequate; captures the basic premise but misses nuance.  
3: Highly faithful; captures the core concepts perfectly.

**Link Quality (Score: 1–3)** is an assessment of the semantic retrieval (RAG) performance when suggesting related notes from the vector store.  
1: Irrelevant connection.  
2: Plausible, but superficial or obvious connection.  
3: Highly useful; reveals a strong, meaningful thematic link.

**System Latency (seconds)** measures the total end-to-end execution time required to read a note and write back its enriched metadata, quantifying the trade-off between execution speed and the anticipated quality improvements of the multi-agent pipeline.

**5\. Related Work**

**Multi-agent orchestration.** AutoGen \[1\] and MetaGPT \[2\] formalize role-specialized agent teams. AgentVerse \[3\] shows specialized teams outperform single agents. Cemri et al. \[4\] presents the first MAS dataset, MAST-Data, a taxonomy of multi-agent failures, and an LLM-based annotator for identifying these failures. These works motivate our comparison between a single general-purpose agent and a structured multi-agent note-processing pipeline.

**RAG systems.** Lewis et al. \[5\] introduced retrieval-augmented generation, where a model retrieves relevant external documents before generating an answer. Our Linker agent follows this idea by retrieving related notes from a ChromaDB vector store before suggesting cross-note links.

**RAG evaluation.** Es et al. \[6\] propose RAGAS, a framework for evaluating RAG systems using metrics such as faithfulness, answer relevance, context relevance, and context recall. This is related to our evaluation because we measure whether the generated summaries are faithful to the original notes and whether the retrieved links are actually useful.

**LLM-as-a-judge evaluation.** Zheng et al. \[7\] study using LLMs as judges for open-ended model outputs through MT-Bench and Chatbot Arena. This is relevant because our project evaluates outputs such as summaries, tags, and related-note suggestions, which are difficult to score with exact-match metrics.

**Self-reflection and overseer agents.** Reflexion \[8\] and Self-Refine \[9\] show that LLMs can improve their outputs through feedback, critique, or revision without fine-tuning. These works motivate our optional overseer agent, which checks the quality of the multi-agent pipeline’s tags, summaries, and suggested links.

**Personal knowledge management and note systems.** Recent note-centric systems such as DeepNote \[10\] and NoteBar \[11\] explore how LLMs can help organize, retrieve, and enrich personal notes. These works are closely related to our Obsidian-based setting because our system also treats notes as personal knowledge units and tries to improve them through tagging, summarization, and semantic linking.

**6\. Resources**

This project will use an AI API or local LLM to power the agents. We will also use a text embedding model to convert notes into vectors for similarity search. Notes will be stored as plain Markdown files in an Obsidian vault, and ChromaDB will serve as the local vector database — persisting each note's filename, embedding, metadata, and raw text so the Linker agent can retrieve semantically similar notes. All orchestration and evaluation scripts will be written in Python.
